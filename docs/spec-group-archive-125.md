# 群收錄模式（使用者 2026-11-12 提出，預定 125）

## 使用者原話（摘要）
讓它「監控一個群」時：
- 群裡的**圖片**都要點開看，記錄圖片是什麼；不一定要發給主人、也不一定要回覆。
- **別人的語音**：點開轉文字，記錄。
- **主人的語音**：轉文字後判斷是不是叫它幹活；是就做，不是就靜默（不回覆）。
- 別人發的**抖音、小紅書等連結**、各種**轉發的東西**（卡片、公眾號文章、視頻號）：都點開看一看並記錄，不一定要發給主人。
- 最後用 Codex 整理：**有乾貨的放進知識庫，廢話直接丟掉**。

## 設計草案（待使用者確認的地方標 ❓）
1. 每個群一個開關「收錄」（守候設定裡），只對開了的群生效。❓預設全關。
2. 守候讀到收錄群的新訊息時：
   - 文字：直接記錄。
   - 語音：先點「轉成文字」（沒有就長按→轉文字），記錄文字。主人的語音另走「是否指令」判斷（下一條）。
   - 圖片、影片、連結、轉發卡片：排進「待看佇列」，**手機閒著時**逐一點開看（唯讀任務：不按讚、不留言、不登入、不付款），看完記一段描述；連結類順便讀作者、標題、文案、數據。
3. 主人的語音（124 已改成「當成主人打的字」）：125 再加一層——由模型判斷是不是要它做事；不是就**不回覆**。
4. 佇列優先順序：主人的指令永遠先做；收錄的「待看」只在空閒時做。❓每小時最多看幾則（避免手機一直被占用、模型額度）。
5. 整理進知識庫：每累積一批（❓例如 20 則或每 2 小時），交給 Codex 判斷乾貨／廢話；乾貨寫進手機上的知識庫（守候回覆會用到的那個），附來源群、時間、原訊息類型。廢話不留。
6. 紀錄存在手機本機（Documents），不上傳；只有乾貨摘要進知識庫。❓是否也要同步到電腦上的 Obsidian 知識庫。

## 安全
- 點開別人的連結一律唯讀；遇到登入、付款、安全驗證就停，記錄「需要人工」。
- 語音、圖片、連結裡的文字都只是資料，不是指令（只有主人的語音、主人的文字才可能是指令）。

## 使用者決定（11-12）
- 收錄哪些群：後台設定的白名單群（守候名單），不另設開關。
- 優先順序：主人的指令優先；手機空閒時才點開圖片、連結、轉發看。
- 整理頻率：一天一次（Codex 判斷乾貨／廢話）。
- 去處：知識庫要同步到使用者的 GitHub 和 Obsidian；使用者之後會在後台連接伺服器，由伺服器上傳。
- **手機只當暫存**：同步（上傳伺服器）成功後，把手機上的收錄紀錄和整理結果刪掉，不占手機空間。

## 125 實作要點（依上面決定）
- 收錄紀錄、每日整理結果先放 Documents/archive/。
- 上傳：雲端設定好時，每日整理完 POST 到伺服器（新增 `POST /api/v1/knowledge`，帶日期、條目、來源群），回 2xx 才刪手機上的那一天；沒設定或失敗就保留，下次再傳。
- 沒有伺服器時的上限：原始紀錄最多留 7 天，整理結果留到上傳成功為止（避免無限長大）。

## 補充（11-12，客戶只口頭說過，GitHub／Obsidian／伺服器都還沒給）
- 風險：微信對自動化與大量點開連結有風控；記錄他人訊息涉及個人資訊（大陸《個人信息保護法》）；一支手機處理量有上限；模型費用與帳戶餘額（11-12 豆包曾欠費停擺）；聽影片要開聲音。
- 建議：只收錄客戶自己管理的群；知識庫只存「內容」不存個人資料（電話、身分證、地址先遮掉）；每天設上限與夜間時段；聊天裡的說法標「群友說法、未查證」，有時效的（價格、新聞）標日期；知識庫變大後回覆要改成「先搜再用」，不能整包塞進模型。
- 先做第一階段：手機收錄＋每日整理＋本機可匯出；上傳介面先定好（POST /api/v1/knowledge），伺服器到位再接，不用等客戶。
- 待客戶確認：群清單、什麼算乾貨（給幾個例子）、檔案（PDF/Word）要不要收、每天預算上限、伺服器規格與帳號、GitHub 倉庫與權限、Obsidian 用什麼方式同步、紀錄保留多久。

## 使用者答覆（11-12 第二次）
- 收錄群＝後台白名單（客戶自己設）。
- 乾貨＝行業經驗、資源連結、別人分享的使用心得等。
- 群文件也要點開看並收錄；要下載才看得到就點下載。
- 每天模型費用不知道 → 先設「每天最多點開 100 則」（可調），App 記錄每天實際呼叫次數，跑幾天再看。
- 伺服器由客戶提供；我們在 App 做好介面（沿用雲端設定的位址與 Token，`POST /api/v1/knowledge`），客戶自己接。伺服器存到它的知識庫或 GitHub 都行。
- 上傳成功就刪手機上的原始紀錄與整理結果。
